# 04 - Security Reporting

## Objective

The reporting component converts the results of automated Nmap scans and security analysis into human-readable security reports.

The purpose is to provide a consistent record of network activity, detected services, security findings, and changes identified during each scan.

---

## Reporting Workflow

```text
Nmap Scan
    |
    v
XML Scan Results
    |
    v
Python XML Parser
    |
    v
Security Analysis
    |
    +------------------+
    |                  |
    v                  v
Port Detection    Baseline Comparison
    |                  |
    +--------+---------+
             |
             v
      Security Findings
             |
             v
       Security Report
```

---

## Report Generation

After each scan, the Python scanner creates a timestamped security report.

Reports are stored in:

```text
reports/
```

The timestamp allows multiple scans to be retained and reviewed separately.

Example:

```text
reports/security_report_2026-10-01_09-30-00.txt
```

This provides a basic historical record of security monitoring activity.

---

## Information Included in Reports

The generated reports can contain information such as:

* Scan timestamp
* Target system
* Open ports
* Detected services
* Security findings
* Newly detected ports
* Closed ports
* Security recommendations

This converts raw Nmap information into a format that can be reviewed by a security analyst.

---

## Example Report

A generated report may contain information similar to:

```text
========================================
AUTOMATED SECURITY REPORT
========================================

Target: 127.0.0.1

Open Ports:

22/tcp - ssh
631/tcp - ipp
8080/tcp - http

Security Findings:

[MEDIUM] FTP detected on port 21

Baseline Changes:

[NEW] Port 8080 detected

Recommendations:

Review newly exposed services and confirm that
they are authorized and properly configured.
```

The exact contents depend on the services detected during the individual scan.

---

## Security Findings

The reporting system records findings generated by the detection component.

For example:

```text
[HIGH] Telnet detected on port 23
```

or:

```text
[MEDIUM] FTP detected on port 21
```

These findings provide an initial signal that a service should be reviewed.

The report does not automatically classify a system as compromised simply because a service is detected.

---

## Baseline Changes

The reporting component also documents changes detected against the security baseline.

For example:

```text
Baseline:

22
631

Current Scan:

22
631
8080
```

The report may identify:

```text
[NEW] Port 8080 detected
```

This allows an analyst to investigate changes to the monitored system.

---

## Observation vs. Security Conclusion

A key principle of this project is separating technical observations from security conclusions.

For example:

```text
Observation:
Port 8080 is listening.

Security consideration:
Determine whether the service is authorized,
properly configured, and required.
```

An open port alone does not establish that a vulnerability or compromise exists.

Additional investigation may be required, including:

* Service identification
* Software version analysis
* Configuration review
* Authentication review
* Firewall analysis
* Vulnerability assessment
* Network exposure analysis

---

## Alert Logging

In addition to generating security reports, the scanner records security findings in:

```text
alerts/alerts.log
```

This provides a separate record of security alerts that can be reviewed independently from the full scan reports.

The combination of reports and alert logs provides both detailed scan information and a simplified record of security findings.

---

## Historical Monitoring

Because reports are timestamped, multiple scans can be retained for historical analysis.

For example:

```text
reports/
├── security_report_2026-10-01_09-00-00.txt
├── security_report_2026-10-01_09-05-00.txt
├── security_report_2026-10-01_09-10-00.txt
└── security_report_2026-10-01_09-15-00.txt
```

An analyst can compare reports over time to identify changes in the monitored environment.

This supports basic security monitoring and change tracking.

## Reporting Use Case

A simplified operational workflow is:

```text
Scheduled Scan
      |
      v
Nmap Results
      |
      v
Security Analysis
      |
      v
Report Generated
      |
      v
Analyst Reviews Findings
      |
      v
Investigate Changes
      |
      v
Document or Remediate
```

This demonstrates how automated security tooling can reduce the amount of manual work required to review recurring network scans.

## Current Limitations

The current reporting system produces text-based reports.

It does not currently provide:

* HTML dashboards
* Graphical visualizations
* Centralized log storage
* Database-backed historical analysis
* Email notifications
* SIEM integration
* Automated ticket creation

The current implementation is intentionally lightweight and designed to demonstrate the core security monitoring workflow.
